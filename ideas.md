# ideas.md — инбокс идей ShikiUpdatesBot

Летучий слой между «искрой» и каноном. Сюда падают сырые мысли, что приходят
по ходу работы и ещё никуда не созрели. Жизненный цикл записи:

  искра → дозрела → переезжает в один из домов:
    • GitHub issue        — задача («что сделать»)
    • AGENTS.md           — процессное решение («как работаем»)
    • ARCHITECTURE.md     — архитектурный факт («как устроено и почему»)
    • секция ⛔ ниже      — отклонённая/отложенная идея (с причиной, паркуется здесь)

Не свалка и не дубль действующего канона. Текущее поведение устанавливают код
и тесты; принятую работу — GitHub issues; процесс — AGENTS.md; устройство бота
и причины решений — ARCHITECTURE.md. Этот файл хранит только незрелые,
отложенные и отклонённые идеи и не переопределяет перечисленные источники.

Файл версионируется в репозитории и синхронизируется между машинами через git.

## 🌱 Идеи (инбокс)

- **Subscriber Control Center.** Настройки подписки вместо нынешнего бинарного
  «подписан / не подписан»: категории событий, режим «только важное», тихая
  доставка, недельный digest, временная пауза и отдельные настройки личных и
  групповых чатов. Публичность `/stats`, `/favs` и `/status` остаётся текущим
  поведением по умолчанию; режимы `approval` / `owner-only` можно обсуждать
  только как опциональную политику конкретного развёртывания. Потребует
  отдельного формата настроек и миграции `subscribers.json`; постоянный журнал
  и очередь уже есть, но сами по себе не задают недельную сводку и предпочтения.
  Сейчас избыточно — не финализировано, issue не заводим.
  Текущие сводки новых событий и объединение добавления/завершения уже работают;
  их [контракт](ARCHITECTURE.md#durable-catch-up-digest) не добавляет недельный digest
  и настройки Subscriber Control Center.

- **Shiki Wrapped / «паспорт вкуса».** Большой аналитический отчёт: отличие
  личных оценок от рейтинга сообщества, любимые и переоценённые жанры, скрытые
  жемчужины, спорные оценки, completion/drop rate по жанрам, изменение вкуса
  со временем и годовые достижения. Выводы должны иметь минимальный размер
  выборки и не притворяться статистически значимыми на нескольких тайтлах.
  Нужны отдельная подготовка аналитических данных и удобный слой агрегирования;
  Rich-отчёты (#10) и периодическое обновление метаданных (#57) уже реализованы.
  Они снимают прежние предпосылки, но не заменяют дизайн аналитики и правила
  достаточной выборки для каждого вывода. Потенциальный результат — пересылаемый
  отчёт или серия карточек. Идея приоритетная, но требует отдельного большого обсуждения.

- **Игра прогнозов для подписчиков.** При начале тайтла подписчики могут
  предсказать итоговую оценку, диапазон оценки или дроп; после завершения бот
  раскрывает результат, начисляет очки и ведёт сезонный рейтинг. Дополнительный
  внешний API не нужен, но понадобятся постоянное состояние игры, связь событий
  начала/завершения и правила для повторного просмотра, смены статуса и тайтлов
  без итоговой оценки. Оставляем настаиваться до отдельного продуктового
  обсуждения.

- **Полноценный групповой режим.** Общая лента уведомлений в выбранном topic,
  а команды, настройки и служебные ответы видит только вызвавший их участник
  через ephemeral-сообщения Telegram Bot API 10.2. Возможность зависит от
  стабильной поддержки в используемой версии aiogram и реального поведения
  клиентов. Ephemeral-доставка официально не гарантируется, особенно офлайн,
  поэтому её нельзя использовать для самой ленты или других критичных данных;
  без прав администратора бот также ограничен коротким окном ответа на действие
  пользователя. Нужен технический spike после созревания библиотечной поддержки.
  Документация: https://core.telegram.org/bots/api#ephemeral-messages-and-commands

- **Расширение постеров в отчётах.** Топ-коллажи и локальные галереи уже
  реализованы; их [действующий контракт](ARCHITECTURE.md#typed-reports-and-interactive-delivery)
  не нужно проектировать заново. Дополнительные карусели или новые места показа
  остаются отложены: пока нет отдельной пользовательской задачи и согласованного
  дизайна, оправдывающих усложнение представления.

- **Многопользовательский режим «я слежу за друзьями».** Сейчас режим «друзья
  следят за мной» (один профиль). Идея: бот проверяет несколько профилей.
  Добавляется в общий чат, настраивается и сообщает туда об активности
  участников (чьи профили добавлены); либо владелец добавляет профили друзей и
  получает уведомления сам. Многопользовательность должна работать со всеми
  функциями: уведомления, статистика, избранное и т.д. Часть нынешних шаблонов
  уведомлений не содержит `{n}`, что допустимо при одном известном профиле, но
  делает источник события неоднозначным при нескольких. При проектировании
  нужен обязательный идентификатор профиля для каждого уведомления — вероятно,
  на общем уровне рендера, чтобы не ломать стиль и не дублировать имя во всём
  банке; окончательный формат отдельно согласовать. Сложность: сложное/
  очень сложное/возможно невыполнимое — помнить про лимиты API Shikimori.
  Не финализировано, issue не заводим. ОТЛОЖЕНО сознательно: не тащим много-
  профильный код поверх незакрытого долга. Триггер возврата — расчищен backlog
  bug/refactor/tech-debt.

## 🧭 Архитектурные заметки на будущее

- **Общий FSM-каркас (fsm_common / bot_utils).** Если понадобится ещё
  разгрузить handlers.py — вынести вниз общие хелперы FSM-обёрток:
  _safe_delete (генерик-чистка сообщений; его зовут и broadcast, и backup, и
  cmd_cancel), возможно _confirm_kb. Тогда тонкие обёртки broadcast/backup
  перестанут тянуть их из handlers — реальная развязка. Это, а не broadcast.py,
  — правильный следующий шаг дробления, если он вообще понадобится.

## ⛔ Отклонено / отложено (с причиной)

Идеи, которые сознательно отвергли. Не обязательно навсегда — что не нужно
сейчас, может пригодиться, когда бот вырастет. У каждой записи — конкретная
причина: вернёшься к идее → перечитай, почему зарубили, и проверь, не изменился
ли контекст. Не перепредлагать без новой причины.

- **Повторная блокировка отслеживания из-за недоступности владельца.**
  Отклонена: остановка лишила бы остальных подписчиков уведомлений. Начальная
  проверка и возобновление через `/start` уже действуют; ошибки владельца во
  время работы обрабатываются в соответствующем сценарии. Потеря единственного
  Telegram-канала бэкапов остаётся риском для хостинга без постоянного диска.
  [Действующий lifecycle](ARCHITECTURE.md#roots-and-lifecycle) принадлежит архитектуре;
  здесь сохраняется причина отказа от повторной блокировки.

- **Постоянно показывать исходное время в каждом catch-up уведомлении.**
  `created_at` нужно сохранить для восстановления и правильного квартала, но в
  обычном сообщении timestamp создаёт больше шума, чем пользы: главное — само
  событие. Дату можно показать только там, где она объясняет задержанный digest
  или корректировку старого периода.

- **Уведомления об удалении и повторном добавлении избранного.** Текущая модель
  намеренно сообщает только о впервые замеченных добавлениях. Удаление требует
  надёжно отличать авторитетный полный snapshot от частичного/повреждённого
  ответа, иначе временный сбой породит ложную массовую рассылку; практическая
  польза пока не оправдывает дополнительное состояние и подтверждение удаления.

- **Бесплатная Authenticode-подпись Windows-релизов через SignPath Foundation.**
  Рассмотреть, если ложные срабатывания Defender/SmartScreen повторятся в
  нескольких релизах или начнут регулярно мешать пользователям. Пока подпись
  отложена: первоначальная настройка и дополнительное ручное одобрение каждого
  релиза не оправданы при отсутствии повторяющейся проблемы.

- **Android как бесплатный постоянно работающий хост для бота.**
  Причина отказа (07.08.2026): надёжная непрерывная работа потребовала бы
  отдельного платформенного приложения, foreground service и обработки сложного
  Android lifecycle. Это фактически второй продукт с несопоставимой текущей
  пользой, а не ещё один простой способ запустить существующий Python-бот.

- **Бэкапы в GitHub Gist (альтернативный канал хранения стейта).**
  Причина отказа (05.08.2026): реализация требует PAT со scope `gist`, Gist ID,
  управления секретами, дополнительной сетевой зависимости, error-handling,
  ротации, restore-логики и сложной настройки со стороны пользователя. Выгода
  ограничена редким двойным отказом: эфемерный хост потерял данные И одновременно
  недоступен Telegram-владелец. Существующие автоматические Telegram-бэкапы
  считаем достаточно надёжным основным каналом. Вернуться к идее можно только
  после реальной потери данных, которую существующий Telegram-канал не
  предотвратил; до такого события не предлагать повторно.

- **Постоянный per-subscriber outbox для истории — прежний отказ пересмотрен.**
  Отказ от 13.08.2026 пересмотрен в [эпике #59](https://github.com/WorgaNomoR/ShikiUpdatesBot/issues/59):
  воспроизводимые потери на границах перезапуска и неопределённый ответ Telegram
  оправдали постоянные обязательства и согласованное восстановление. Очередь,
  сводки и безопасная очистка реализованы; [действующие контракты](ARCHITECTURE.md#durable-journal-notification-delivery)
  описываются в ARCHITECTURE, без отдельной истории каждого дочернего этапа здесь.
  Настройки подписчиков, недельные сводки и восстановление недоступной источнику
  истории остаются отдельными решениями. Бессрочный аудит удалённых исходов и
  бесконечная вместимость не приняты: практическая польза не оправдывает
  неограниченный рост, а сохранение точных ID и необходимых источников обязательно.

- **«Problem B» — бэкафилл stats_current из истории.**
  Причина: Отклонено по причине невозможности полностью достоверного воссоздания
  пропущенных событий. Действующая статистика по времени события восстанавливает только доступные
  принятые события с достоверным временем, сохраняя явную неполноту. Она не
  пересчитывает legacy-базу при миграции и не восстанавливает недоступные
  источнику события. [Поправки в следующем отчёте](ARCHITECTURE.md#event-time-quarterly-projections)
  уже реализованы; немедленные сообщения и автоматическое переосмысление
  сомнительных дат остаются отложены без отдельного обоснования.

- **Джиттер интервала поллинга.**
  Причина: фиксированный интервал намеренно (firewall-философия) — предсказуемый
  ритм важнее размазывания нагрузки и рестартов.

- **Оценка 4 в отдельный/низкий банк оценок.**
  Причина: остаётся в mid. Без выделенного бакета четвёрку чисто не отделить, а
  ради редкого случая отдельный бакет не оправдан.

- **Выделение /broadcast в отдельный модуль (broadcast.py).**
  Причина: нечего выносить. В отличие от backup (толстая логика: zip/restore/
  валидаторы/триггеры/send_backup), у broadcast вся «логика» — одна функция
  _send_broadcast_message; остальное тонкие FSM-обёртки (cmd_broadcast,
  broadcast_receive/confirm/cancel), намертво сидящие на общем каркасе
  (_safe_delete — генерик; cmd_cancel — одна команда на оба FSM). Вынос дал бы
  тот же цикл handlers↔broadcast, что разруливали у бэкапа, но без выгоды.
  NB: send_to_all_chats обслуживает уведомления об избранном
  (check_and_notify_favourites), не broadcast, так что с ним бы и не уехала.
  Нужна разгрузка handlers — см.
  fsm_common в 🧭, не broadcast.py.

- **Схлопывание «избыточного» init-блока polling_loop.**
  Причина: после boot-throttle перестало быть избыточным. init теперь несёт
  реальный смысл — общая ClientSession на старте + фетч favourites один раз для
  sync(fav=); схлопывание увело бы первый baseline в цикловые check_and_notify*
  (каждая со своей сессией) → менее throttled старт + двойной фетч favourites.
  А baseline в check_and_notify* — не дубль, а намеренная 429-резильентность
  (fallback, если стартовый фетч упал из-за 429/сети). Слоистость init=primary /
  check=fallback оставляем. Дедуп-фолд закрыт частью 1 (общий хелпер отписки).

- **Форс пустых строк через ruff E3 (E301–E306).**
  Причина: в нашей версии ruff эти правила preview-gated («has no effect because
  preview is not enabled») — включение требует preview=true, а это тянет пачку
  нестабильных preview-правил ради одних пустых строк — непропорционально.
  Стабильный путь к «воздуху» — ruff format (сам ставит 2 строки между top-level
  def), но это репо-широкий реформат = отдельное решение/ветка, не сейчас. Пока
  «воздух в коде» — на человеческий глаз.

- **Ручной `/resync` (owner-only форс `sync_stats_all` вне расписания).**
  Причина: отладочный форс уже покрыт рестартом (бут ресинкает `sync_stats_all`
  безусловно); recovery после упавшего синка тоже авто — при неудаче
  `last_full_sync=None`, и `_should_full_sync` даёт `True` каждый цикл, пока не
  пройдёт (≤ `CHECK_INTERVAL`); юзер-выигрыш мал — горячие данные (история/
  избранное) и так проверяются каждые 15 мин, отстаёт лишь 6-часовой агрегат
  `stats_all`, где свежесть некритична. Честная реализация (немедленно + без
  гонки с цикловым синком за `stats_all.json` через `_atomic_write`) требует
  общего `asyncio.Lock` между командой и `polling_loop` — сложность
  непропорциональна редкому удобству. Вернуться, если: часто нужен ручной форс
  при отладке; ИЛИ многопрофильный режим сделает on-demand-обновление
  осмысленным; ИЛИ статистика станет время-чувствительной. NB: центральный
  троттл (ветка rate-limit) уже снял 429-риск ручного берста — реализация стала
  безопаснее.

- **Defensive `quote()` на `SHIKI_USER` в URL-билдерах** (`shiki_api.py`:
  `HISTORY_URL`/`FAVOURITES_URL`/`LIST_EXPORT_*`/rates).
  Причина: ник — доверенный константный env-вход, задаётся по charset-правилам
  Shikimori. Структурные для URL символы (`/ ? #`) при регистрации просто
  вырезаются — эмпирика: ник `Wtgsea/?#` сохранился как `Wtgsea`. Легальную
  экзотику (math-script глифы вроде `𝓕𝓵𝓾𝓯𝓯𝔂`, `+`, пробел) `yarl` внутри aiohttp
  уже корректно percent-энкодит (проверено в песочнице на всех кейсах: не-ASCII →
  %F0.., пробел → %20, `+` литеральный = верно для пути). Threat model «инъекция
  извне» отсутствует. Практической выгоды ноль, риск переусложнения. Вернуться —
  только если появится недоверенный источник ника (напр. мультипрофиль, где ник
  берётся из пользовательского ввода, а не из env).
