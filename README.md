Telegram-бот, который следит за аниме, мангой и ранобэ любого пользователя на [Shikimori](https://shikimori.io) и отправляет подписчикам весёлые уведомления о каждом событии: что человек начал смотреть, бросил, оценил или добавил в избранное.

Достаточно указать ник отслеживаемого пользователя — и бот готов к работе (отображаемое имя можно задать отдельно, но не обязательно). Никаких ключей API и авторизаций: всё работает на публичных данных Shikimori.

## Что умеет

- 📡 Проверяет историю и избранное пользователя каждые **15 минут**
- ⏪ После перерыва в работе догоняет пропущенные изменения на Shikimori
- 🎬 Реагирует на события: добавил в список, начал смотреть/читать, пересматривает/перечитывает, отложил, бросил, завершил, поставил или изменил оценку
- 🔕 Намеренно не присылает служебные записи о прогрессе по эпизодам, главам и томам, удалении из списка и отмене оценки
- ⭐ Отслеживает новые добавления в избранное: аниме, мангу, ранобэ, персонажей и людей индустрии
- ✅ Поддерживает **аниме** (TV, фильм, OVA, ONA), **мангу** (кроме ваншотов и додзинси) и **ранобэ**
- 📋 Показывает, что отслеживаемый пользователь смотрит и читает прямо сейчас
- 📊 Собирает **статистику** просмотренного и прочитанного: жанры, темы, аудитория, студии, издатели, источники адаптации, годы выпуска, оценки и сравнение со средним рейтингом Shikimori
- 🗓️ В начале каждого квартала автоматически присылает владельцу **развёрнутый отчёт** с достижениями и сравнением с прошлым кварталом
- ❤️ Показывает избранное — любимые аниме, мангу, ранобэ, персонажей и людей индустрии, со ссылками и оценками
- 📢 Владелец может обратиться ко всем подписчикам одним сообщением
- 💾 Резервное копирование всех данных — автоматическое (при подписках/отписках, смене квартала и еженедельно) и ручное одной командой; source/Docker дополнительно сохраняются перед плановой остановкой
- 👥 Система подписки — каждый подписывается сам командой `/start`
- 🩺 HTTP-эндпоинт `/health` для healthcheck — совместимость с хостингами и автоперезапуск при зависании
- ⚠️ При ошибках фоновой проверки пишет в лог и уведомляет владельца в Telegram (с антиспамом)

## Команды

| Команда | Описание |
|---|---|
| `/start` | Подписаться на уведомления |
| `/stop` | Отписаться |
| `/status` | Что отслеживаемый пользователь смотрит и читает прямо сейчас |
| `/stats` | Статистика — открывает меню с кнопками выбора отчёта |
| `/favs` | Избранное: любимые аниме, манга, ранобэ, персонажи и люди индустрии |
| `/broadcast` | Написать сообщение подписчикам *(только для владельца)* |
| `/cancel` | Отменить текущую операцию *(только для владельца)* |
| `/subs` | Список подписчиков с кликабельными ссылками на профили *(только для владельца)* |
| `/backup` | Экспорт/импорт всего состояния архивом *(только для владельца)* |
| `/version` | Версия бота, режим запуска, последний GitHub Release и ссылки на проект *(только для владельца)* |

## Статистика и отчёты

Бот ведёт статистику активности отслеживаемого пользователя и строит по ней наглядные отчёты с выровненными колонками, процентами и распределением оценок.

**Команда `/stats`** открывает меню с кнопками — можно выбрать статистику **за текущий квартал** или **за всё время**. Выбрал кнопку → пришёл отчёт, само меню удаляется, чтобы не захламлять чат. Есть и быстрый путь: `/stats all` сразу присылает статистику за всё время, минуя меню.

**Квартальный отчёт** формируется автоматически при смене квартала (1 января, апреля, июля, октября) и отправляется владельцу. Он включает полную статистику за квартал, сравнение с предыдущим и блок «достижений». Если бот был выключен в момент смены квартала — отчёт сформируется при следующем запуске (с защитой от повторной отправки).

**Что считается:** завершённое, брошенное и добавленное в планы, средняя оценка и её распределение, топ по оценкам, разбивка по жанрам / темам / аудитории, студии (для аниме) и издатели (для манги и ранобэ), источники адаптации, возрастные рейтинги, хронология по годам, примерное время просмотра и количество глав, а также сравнение личных оценок со средним рейтингом Shikimori.

**Откуда данные.** Списки пользователя (что просмотрено, оценки, прогресс) берутся из публичного экспорта Shikimori — без авторизации. Метаданные тайтлов (жанры, студии, год и т.д.) подтягиваются через GraphQL API батчами, только для новых тайтлов. Команды `/stats` и `/favs` читают готовые локальные файлы и не делают сетевых запросов — отвечают мгновенно и не зависят от доступности Shikimori.

При первом запуске в середине квартала статистика за текущий квартал будет неполной — об этом честно пишется в заголовке (`статистика с DD.MM.YYYY`). А статистика за всё время строится сразу и полностью, потому что берётся из экспорта списков, а не из накопленных событий.

Версии до `v0.2.5` могли ошибочно принять запись о прогрессе за полное завершение. Уже сохранённую ложную запись нельзя исправить автоматически: `stats_current.json` не хранит исходное описание Shikimori, поэтому бот не может надёжно отличить её от настоящего завершения.

## Избранное

**Команда `/favs`** показывает любимое — список избранного со ссылками на Shikimori и проставленными оценками (там, где они есть). Учитываются все категории избранного Shikimori: аниме, манга, ранобэ, персонажи и люди индустрии. Пустые категории не показываются.

Это намеренно отдельная от статистики история: в `/stats` — агрегаты и цифры, в `/favs` — то, что человек выделил как любимое. Поэтому избранное живёт в своей команде, а не в общем отчёте.

## Запуск

Универсально лучшего способа нет: локальный EXE проще настроить, а хостинг лучше
подходит для круглосуточной работы. Честное сравнение:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Portable EXE для Windows** | Не нужны GitHub, Python, терминал и установка; все файлы в одной папке | Только Windows x64; компьютер и консоль должны постоянно работать |
| **Python из исходников** | Работает на разных ОС; проще изменять и отлаживать код | Нужны Python, терминал и ручное управление зависимостями/обновлениями |
| **Хостинг через GitHub** | Работает 24/7 без домашнего компьютера; обычно есть автоперезапуск | Нужны аккаунты GitHub и хостинга, настройка переменных и постоянного диска; условия и цены платформ меняются |
| **Docker на своём сервере** | Максимальный контроль, предсказуемое хранение и обновление | Нужны сервер и навыки администрирования Docker |

В любом варианте понадобятся три значения — если чего-то не хватает, бот скажет
об этом на старте:

**Токен бота** (`BOT_TOKEN`). Напиши [@BotFather](https://t.me/BotFather) →
команда `/newbot` → следуй инструкциям → получи токен.

**Свой Telegram ID** (`OWNER_ID`). Напиши
[@userinfobot](https://t.me/userinfobot) — он пришлёт твой числовой ID. По нему
бот узнаёт владельца для административных команд и сообщений об ошибках.

**Ник на Shikimori** (`SHIKI_USER`). Пользователь, за историей и избранным
которого следит бот. Отсюда же берётся имя в сообщениях; при желании его можно
переопределить через `DISPLAY_NAME`.

**После первого запуска подпишись на своего бота.** Открой его в Telegram и
нажми `/start`: только после успешной проверки связи запустится фоновое
отслеживание. Это также позволяет получать аварийные сообщения и собственные
рассылки в том же виде, что и остальные подписчики.

Полностью распакуй ZIP в доступное для записи место и запусти
`ShikiUpdatesBot.exe`. Не запускай exe прямо из архива и не помещай portable-папку
в `Program Files`.

При первом запуске exe скопирует `.env.example` в `.env` и остановится. Открой
созданный `.env`, заполни `BOT_TOKEN`, `OWNER_ID` и `SHIKI_USER`, затем запусти
exe снова. По умолчанию все постоянные файлы остаются внутри одной portable-папки:

```text
ShikiUpdatesBot/
├── ShikiUpdatesBot.exe
├── .env
├── .env.example
├── README-Windows.txt
├── LICENSE.txt
├── data/
└── logs/
```

`.env` и `logs/` всегда остаются рядом с exe. Только каталог состояния `data/`
можно намеренно перенести через `DATA_DIR`; относительный путь считается от
portable-папки, а абсолютный используется как указан.

Бот работает, только пока компьютер включён, не спит и окно консоли открыто.
Healthcheck-сервер в exe не запускается — на домашнем ПК он не нужен и не должен
вызывать запрос Windows Firewall.

Полезные команды из PowerShell:

```powershell
.\ShikiUpdatesBot.exe --check-config
.\ShikiUpdatesBot.exe --version
```

EXE проверяет последний полноценный GitHub Release не чаще раза в сутки. При
новой версии владелец один раз получает сообщение с кнопкой на страницу релиза;
команда `/version` показывает версию, сведения о проекте и проверяет релиз
вручную. Ничего не скачивается и не заменяется автоматически. Для обновления
останови бот и замени только exe —
`.env`, `data/` и `logs/` сохраняются.

> рекомендуется. Проверяй, что архив скачан с ожидаемой страницы Release; рядом
> с ним публикуется SHA-256. Для прозрачности релизный EXE также автоматически
> отправляется в VirusTotal, а результат или честное сообщение о недоступности
> анализа добавляется в описание релиза. Эта проверка информационная и не
> заменяет самостоятельную оценку исходников и процесса сборки.

Подробная инструкция находится в `README-Windows.txt` внутри архива.

#### Б. Запуск из исходников

Подходит для разработки, других операционных систем или если нужен полный
контроль над Python-окружением.

```bash
# 1. Клонировать репозиторий
git clone https://github.com/WorgaNomoR/ShikiUpdatesBot.git
cd ShikiUpdatesBot

# 2. Установить зависимости
pip install -r requirements.txt

# 3. Запустить из корня репозитория после настройки .env
python main.py
```

Перед запуском скопируй `.env.example` в `.env` и заполни три обязательных
значения. Файл читается из корня репозитория; уже заданные системные переменные
не перетираются. В этом режиме `/version` показывает ту же версию проекта,
сведения о боте и по запросу владельца проверяет последний Release. Автоматические
уведомления о новых EXE здесь не запускаются: исходники обновляются через Git.

Как и EXE, локальный Python-процесс остановится при закрытии терминала, выключении
или сне компьютера. В отличие от EXE, source-режим запускает healthcheck-сервер.

### Вариант 2. Хостинг через GitHub — для работы 24/7

Это не самый простой старт: нужны отдельные аккаунты GitHub и хостинг-платформы,
а также внимательная настройка хранилища. Зато бот работает независимо от
домашнего компьютера и обычно автоматически перезапускается после сбоя.

Общая схема для платформ, которые умеют собирать репозиторий по `Dockerfile`:

1. Сделай форк репозитория в свой GitHub-аккаунт.
2. Создай проект на выбранной хостинг-платформе и подключи форк.
3. Задай секретные переменные `BOT_TOKEN`, `OWNER_ID` и `SHIKI_USER`.
4. Если платформа спрашивает Healthcheck Path, укажи `/health`.
5. Подключи persistent volume/disk к пути `/data`.
6. Проверь логи первого запуска и отправь боту `/start`.

> ⚠️ Без постоянного диска каталог `/data` обычно эфемерен: подписчики,
> статистика и квартальные данные могут исчезнуть при редеплое. Telegram-бэкапы
> помогают восстановиться, но не заменяют правильно подключённый том.

При выборе платформы заранее проверь пять вещей: непрерывность работы бесплатного
тарифа, поддержку volume на `/data`, лимиты исходящего трафика, способ оплаты и
возможность остановить/перезапустить сервис. Эти условия меняются, поэтому README
намеренно не объявляет ни одну платформу «навсегда бесплатной». Например,
[Railway](https://docs.railway.com/volumes/reference) поддерживает persistent volumes; также можно
рассмотреть [apply.build](https://apply.build), [bothost.ru](https://bothost.ru)
или другую Docker-совместимую платформу, проверив её текущие условия.

### Вариант 3. Docker на своём сервере

Подходит, если у тебя есть VPS или постоянно включённый сервер и опыт работы с
Docker. Это самый гибкий, но и самый требовательный к администрированию вариант.

Как и в других способах, `BOT_TOKEN`, `OWNER_ID` и `SHIKI_USER` задаются в
корневом `.env`. Compose передаёт из этого же файла и все необязательные
настройки: скопируй `.env.example` в `.env`, затем заполни обязательные значения
и при необходимости раскомментируй остальные.

```bash
# 1. Скопируй .env.example в .env и заполни:
#    BOT_TOKEN=токен_от_BotFather
#    OWNER_ID=твой_telegram_id
#    SHIKI_USER=ник_на_shikimori

# 2. Собери и запусти контейнер
docker compose up -d --build

# 3. Логи
docker compose logs -f

# 4. Остановить
docker compose down
```

Для обновления после изменений в коде:

```bash
docker compose up -d --build
```

Данные бота хранятся в `/data` внутри контейнера; `docker-compose.yml` монтирует
туда локальную папку `./data`, поэтому состояние переживает пересборку. Compose
намеренно фиксирует `DATA_DIR=/data`: значение `DATA_DIR` из корневого `.env` не
может отсоединить состояние от этого тома. Если healthcheck должен быть доступен
снаружи контейнера, добавь проброс порта:

```yaml
    ports:
      - "8080:8080"
```

Если в `.env` задан другой `PORT`, с ним должен совпадать внутренний порт справа;
внешний порт слева можно выбрать отдельно. Например, для `PORT=9090` подходит
проброс `"8080:9090"`.

## Healthcheck

При Python/Docker-запуске бот поднимает лёгкий HTTP-сервер параллельно с основным
циклом (модуль `healthcheck.py`). В portable Windows exe он намеренно отключён.
На хостинге сервер нужен для двух целей:

- **Совместимость с хостингами**, которые требуют открытый порт или healthcheck-эндпоинт (Render, Fly.io, Cloud Run и подобные). Без него такие платформы могут считать, что процесс не запустился.
- **Watchdog**: эндпоинт `/health` отдаёт `200`, только если бот «пульсирует» — недавно успешно завершил итерацию фонового цикла. Если пульс протух (цикл завис или умер) — отдаётся `503`, и хостинг с настроенным healthcheck перезапустит контейнер.

| Эндпоинт | Ответ |
|---|---|
| `GET /health` | `200` если бот жив, `503` если последний успешный цикл был давно |
| `GET /` | `200` — простой признак, что порт открыт |

**Порог живости** адаптивный — три пропущенных цикла (`CHECK_INTERVAL × 3`, по умолчанию 45 минут). **Порт** берётся из переменной окружения `PORT` (хостинги обычно прокидывают её сами), по умолчанию `8080`. В настройках хостинга в качестве Healthcheck Path укажи `/health`.

**Настройки liveness-пробы.** Порог в 45 минут и подсчёт пропущенных циклов
уже внутри `/health`, поэтому проба платформы должна быть тонким частым
триггером, а не считать провалы сама:

| Параметр | Рекомендация |
|---|---|
| Interval | ~60 сек — **не** ставь большой интервал (40+ мин): проба проскочит переход в `503`, и бот пролежит вдвое дольше |
| Max failures | 1–2 (`503` уже значит «точно мёртв 45 минут») |
| Timeout | ~10 сек |
| Initial delay | ~15–20 сек |

«Сколько простоя до перезапуска» меняется в коде (`CHECK_INTERVAL × misses`),
а не увеличением интервала пробы.

Дополнительных зависимостей не требуется — используется серверная часть уже установленного `aiohttp`.

## Конфигурация

Все параметры задаются переменными окружения (читаются в `config.py`):

| Переменная | По умолчанию | Описание |
|---|---|---|
| `BOT_TOKEN` | из переменной окружения | Токен Telegram-бота от BotFather |
| `OWNER_ID` | из переменной окружения | Telegram ID владельца для админ-команд и уведомлений об ошибках |
| `SHIKI_USER` | из переменной окружения | Ник отслеживаемого пользователя на Shikimori |
| `DISPLAY_NAME` | ник из `SHIKI_USER` | Имя в сообщениях; подходящее русское имя автоматически склоняется |
| `DISPLAY_NAME_GENDER` | `auto` | Режим грамматики имени: `auto`, `male`, `female` или `none` |
| `SHIKI_BASE_URL` | `https://shikimori.io` | Домен Shikimori — менять при смене зеркала |
| `CHECK_INTERVAL` | `900` (15 мин) | Интервал проверки в секундах |
| `ERROR_NOTIFY_INTERVAL` | `1800` (30 мин) | Минимальная пауза между уведомлениями владельцу об ошибках |
| `FULL_SYNC_INTERVAL` | `21600` (6 ч) | Как часто фоновый цикл пересинхронизирует полную статистику (`stats_all`) |
| `DATA_DIR` | `/data`; в exe — `data/` рядом с exe | Папка для файлов состояния; относительный override в exe считается от portable-папки |
| `PORT` | `8080` | Порт healthcheck-сервера для Python/Docker; portable exe его не запускает |

Чтобы отслеживать другого пользователя — задай переменную окружения `SHIKI_USER`. Отображаемое имя бот возьмёт из ника автоматически; при желании переопредели его переменной `DISPLAY_NAME`.

Обычная настройка требует только одного значения, например `DISPLAY_NAME=Костя`: при запуске бот получит формы `Кости`, `Косте`, `Костю`, `Костей` и выберет мужские варианты слов. Автоматическая грамматика применяется только к русским буквам с необязательными дефисами; ники с пробелами, латиницей, цифрами, подчёркиваниями, эмодзи или другой пунктуацией остаются без изменений.

`DISPLAY_NAME_GENDER` нужен лишь как запасной переключатель. `auto` определяет пол автоматически; `male` или `female` принудительно задают его для любого поддерживаемого русского имени и обычно полезны для неоднозначных имён вроде `Саша` и `Женя`; `none` полностью отключает склонение и оставляет прежние мужские формулировки. Если имя не распознано или библиотека грамматики дала сбой, бот безопасно использует исходное имя и продолжает запуск.

## Поведение при ошибках

Фоновый цикл проверки не останавливается из-за единичной ошибки Shikimori API, сети, парсинга или отправки сообщения. Бот:

- пишет полный traceback в лог;
- пробует отправить владельцу короткое сообщение об ошибке в Telegram;
- не шлёт такие уведомления чаще одного раза в `ERROR_NOTIFY_INTERVAL`;
- продолжает работу и повторяет проверку после `CHECK_INTERVAL`.

Сбор статистики устроен так же отказоустойчиво: недоступность экспорта или GraphQL не роняет бота — отчёт просто выйдет без обогащённых метаданных, а битый файл состояния заменяется пустой структурой. Команды `/stats` и `/favs` не делают сетевых запросов и не могут упасть из-за недоступности Shikimori.

Если процесс Python полностью завершился, сервер выключился или Telegram недоступен, уведомление об ошибке отправить уже не получится — в таких случаях помогут логи хостинга или внешний мониторинг (для последнего и пригодится healthcheck-эндпоинт).

## Файлы данных

Бот хранит файлы состояния — **их не нужно коммитить** (они уже в `.gitignore`):

- `seen_ids.json` — ID уже обработанных событий истории
- `subscribers.json` — список подписчиков
- `seen_favourites.json` — ID уже обработанных записей избранного
- `stats_all.json` — статистика за всё время: архив тайтлов, агрегаты и избранное
- `stats_current.json` — события текущего квартала
- `update_state.json` — состояние проверки GitHub Releases и последнего уведомления
- `quarters/` — замороженные снапшоты завершённых кварталов

При Python/Docker-запуске файлы по умолчанию создаются в `/data`; portable exe
использует `data/` рядом с собой. Чтобы намеренно переопределить путь, укажи:

```
DATA_DIR=/путь/к/папке
```

При первом запуске бот молча запоминает текущую историю и избранное и не спамит прошлыми событиями — отслеживает только новые.

## Резервное копирование и перенос состояния

Команда `/backup` (только для владельца) открывает меню с двумя кнопками:

- **📤 Экспорт** — бот присылает zip-архив всего каталога `/data`: подписчики, статистика за всё время, текущий квартал и снапшоты прошлых кварталов.
- **📥 Импорт** — пришли боту такой архив файлом, и он восстановит **подписчиков, текущий квартал, снапшоты кварталов и состояние проверки обновлений**. Поэтому после переноса бот не повторит уже доставленное уведомление о той же версии. Остальное (служебные `seen_*` и `stats_all`, которые бот и так пересобирает сам) из архива намеренно игнорируется.

**Перенос при смене хостинга:** на старом хостинге `/backup` → 📤 Экспорт, сохрани архив. На новом — запусти бота, затем `/backup` → 📥 Импорт и пришли архив.

> ⚠️ После выгрузки архива обязательно останови (или удали) бота на старом хостинге, прежде чем поднимать на новом. Два процесса с одним `BOT_TOKEN` начнут конфликтовать за `getUpdates` (Telegram отдаёт «terminated by other getUpdates request»), и оба будут работать нестабильно.

**Авто-бэкап.** Помимо ручного экспорта, бот сам присылает владельцу свежий архив (с тегом `#backup`) при каждой подписке/отписке (заодно — уведомление, кто именно, со ссылкой на профиль), при смене квартала и раз в неделю. Source/Docker-режим дополнительно делает финальный снапшот перед плановой остановкой (`SIGTERM` при редеплое). На эфемерных хостах без тома на `/data` это единственный способ не потерять список подписчиков между редеплоями.

Portable EXE намеренно не делает shutdown-бэкап: локальная папка `data/` постоянна, а архив при каждом закрытии консоли или выключении компьютера только засорял бы чат. Плановые и событийные копии продолжают работать. На source/Docker-хостинге shutdown-бэкап остаётся подстраховкой: он ловит плановую остановку, но не аварийную (`SIGKILL`/нехватка памяти/слишком короткий grace-период).

> 💡 Доставка авто-бэкапов идёт владельцу напрямую по `OWNER_ID`, поэтому владелец должен хотя бы раз нажать `/start` — иначе Telegram не даст боту написать первым (та же причина, по которой важно быть подписанным; см. раздел запуска).

## Рассылка сообщений подписчикам

1. Напиши боту `/broadcast`.
2. Пришли сообщение для рассылки — поддерживаются текст, фото, видео, GIF, стикер, документ, голосовое.
3. Бот покажет превью и предложит две кнопки: **📢 Отправить** или **❌ Отмена**.
4. Если передумал до отправки превью — напиши `/cancel`.

## Разработка и тестирование

Внутреннее устройство и принятые технические решения описаны в [ARCHITECTURE.md](ARCHITECTURE.md). Правила работы с репозиторием — в [AGENTS.md](AGENTS.md).

```bash
pip install -r requirements.txt -r requirements-dev.txt
```

Запуск тестов:

```bash
pytest tests/                        # все тесты
pytest tests/test_notify.py -v       # конкретный файл, подробный вывод
pytest tests/ -v --cov               # с измерением покрытия
```

**Важно:** тесты требуют переменные окружения `BOT_TOKEN` и `OWNER_ID` — они автоматически выставляются в `tests/conftest.py`, отдельно настраивать ничего не нужно.
