ShikiUpdatesBot — Telegram-хаб публичного профиля
[Shikimori](https://shikimori.io). Через единое меню `/start` прямо в Telegram можно посмотреть
текущую активность и статистику профиля, избранное, а также списки аниме, манги и ранобэ с
распределением тайтлов по статусам. Отдельно доступны интересные факты об аниме и Японии и сведения
о самом боте. Все эти возможности работают без подписки.

При желании бот присылает уведомления о новых событиях профиля: начале просмотра или чтения,
изменении статуса и оценки, завершении и добавлении в избранное. Подписка включается и отключается
только после подтверждения. Подписчики и владелец могут прямо из любого чата Telegram искать на
Shikimori аниме, мангу и ранобэ и отправлять их карточки собеседникам. Владельцу также доступны
квартальные отчёты, резервные копии, каталог пользователей и рассылка. Входить в аккаунт
Shikimori не нужно, но список отслеживаемого профиля должен быть открыт для всех пользователей
сайта.

Обычному пользователю рекомендуется portable-версия для Windows. Для ожидаемой работы 24/7 лучше
подойдёт хостинг, который не зависит от включённого домашнего компьютера.

## Руководство пользователя

### Что делает бот

- 📡 Каждые 15 минут проверяет историю и избранное пользователя. После следующего запуска пытается
  догнать недавние события, пропущенные пока бот не работал.
- 🔔 Присылает уведомления о добавлении в «Запланировано», начале просмотра или чтения, пересмотре
  или перечитывании, откладывании, завершении, изменении оценки и других значимых действиях.
  Прогресс по эпизодам, главам и томам, удаление из списка и отмена оценки игнорируются.
- ✅ Поддерживает аниме-сериалы, фильмы, OVA и ONA; мангу (кроме ваншотов и додзинси); ранобэ.
- ⭐ Отслеживает избранные аниме, мангу, ранобэ, персонажей и людей индустрии.
- 📋 Показывает текущие просмотры и чтение, списки запланированных, просматриваемых, завершённых,
  отложенных и брошенных аниме, манги и ранобэ, а также избранное и статистику.
- 🔎 Позволяет подписчикам искать аниме, мангу и ранобэ прямо из любого Telegram-чата и отправлять
  готовые карточки с постером, оценкой, первоисточником, возрастным рейтингом, статусом, фактами,
  жанрами и скрытым описанием.
- 🗓️ В начале квартала отправляет владельцу отчёт с итогами и сравнением с прошлым кварталом.
- 📢 Позволяет владельцу отправлять сообщения всем подписчикам.
- 🚫 Позволяет владельцу закрыть выбранным Telegram-пользователям доступ ко всем функциям бота.
- 💾 Создаёт Telegram-бэкапы и позволяет переносить данные бота между компьютером и хостингом.

Подробнее о проверке событий и восстановлении после перерыва рассказано в
[техническом справочнике](#хранение-данных-и-жизненный-цикл).

### Какой способ запуска выбрать

**Portable-версия для Windows — рекомендуемый вариант для обычного пользователя.** Не требует
Python, Docker, GitHub или установки программы. Компьютер при этом должен быть постоянно включён,
не переходить в сон и иметь стабильное соединение с Telegram и Shikimori.

Если запускать бота только время от времени, он будет работать отдельными сессиями. Пока бот
выключен, команды не обрабатываются. После следующего включения он попытается догнать недавние
события и может прислать сразу несколько уведомлений. Очень долгий или насыщенный событиями перерыв
может оказаться слишком большим: тогда часть старых событий уже не удастся найти. Поэтому локальный
запуск не заменяет работу 24/7.

**Хостинг из GitHub-репозитория — самый простой из продвинутых вариантов.** Он подходит, если бот
должен ожидаемо работать круглосуточно без домашнего компьютера. Понадобятся аккаунты GitHub и
хостинг-платформы, переменные окружения и постоянный диск. См.
[инструкцию для хостинга](#хостинг-из-github-репозитория).

**Python из исходников** удобен для разработки, других операционных систем и ручного контроля
окружения. См. [запуск через Python](#запуск-через-python).

**Docker Compose** подходит для собственного VPS или постоянно включённого сервера. См.
[запуск через Docker](#запуск-через-docker-compose).

> [!WARNING]
> Работа Telegram в России
> [ограничивается](https://www.interfax.ru/digital/1072012), поэтому соединение локального бота с
> Telegram может быть нестабильным или недоступным: команды, получение обновлений и отправка
> сообщений способны задерживаться или прекращаться. Хостинг в сети без таких ограничений часто
> надёжнее для работы 24/7, но его доступность тоже зависит от провайдера и сетевого маршрута.
> Ограничения могут меняться; проверяйте актуальную ситуацию перед выбором места запуска.

### Что нужно подготовить

Независимо от способа запуска нужны три значения:

1. **Токен Telegram-бота — `BOT_TOKEN`.** Напишите
   [@BotFather](https://t.me/BotFather), отправьте `/newbot` и следуйте инструкциям. Токен даёт
   полный контроль над ботом: никому его не передавайте и не публикуйте.
2. **Telegram ID владельца — `OWNER_ID`.** Его можно узнать у
   [@userinfobot](https://t.me/userinfobot). Это числовой ID пользователя, которому доступны
   административные команды, бэкапы и сообщения об ошибках.
3. **Ник на Shikimori — `SHIKI_USER`.** Это профиль, под который настраивается бот: его история,
   текущие просмотры и чтение, избранное и статистика будут использоваться в уведомлениях, командах
   и квартальных отчётах. Отображаемое имя при желании задаётся отдельно через `DISPLAY_NAME`.

Чтобы искать аниме, мангу и ранобэ из любого Telegram-чата и отправлять найденные
карточки, дополнительно включите inline mode у [@BotFather](https://t.me/BotFather): отправьте
`/setinline`, выберите бота и задайте подсказку, например
`а Берсерк · м Higurashi · р Re:Zero`. Без этой настройки поиск в поле сообщения не появится.
Подробнее о доступе и формате запроса — в разделе
[«Поиск тайтлов из любого чата»](#поиск-тайтлов-из-любого-чата).

> [!IMPORTANT]
> У отслеживаемого профиля настройка **«Могут видеть мой список»** должна иметь значение
> **«Все посетители сайта»**. Владелец профиля может изменить её после входа на страницу
> `https://shikimori.io/ВАШ_НИК/edit/profile`. Закрытый список делает недоступными историю,
> выгрузку списков и данные для `/status`: уведомления и статистика перестанут обновляться. Бот
> отличит эту настройку от временного сбоя и пришлёт владельцу инструкцию с готовой ссылкой;
> остальным пользователям `/status` покажет только краткое объяснение. Бот использует только
> публичные данные и не может обойти приватность профиля.

1. Полностью распакуйте ZIP в доступную для записи папку. Не запускайте exe прямо из архива и
   не помещайте portable-папку в `Program Files`.
2. Запустите `ShikiUpdatesBot.exe`. При первом запуске он создаст `.env` из `.env.example` и
   остановится. Существующий `.env` никогда не перезаписывается.
3. Откройте `.env`, заполните `BOT_TOKEN`, `OWNER_ID` и `SHIKI_USER`, затем сохраните файл.
4. Снова запустите `ShikiUpdatesBot.exe` и не закрывайте консоль во время работы.
5. Откройте чат с ботом в Telegram и отправьте `/start`.

По умолчанию все постоянные файлы остаются в одной папке:

```text
ShikiUpdatesBot/
├── ShikiUpdatesBot.exe
├── Enable-Autostart.cmd
├── Disable-Autostart.cmd
├── .env
├── .env.example
├── README-Windows.txt
├── LICENSE.txt
├── data/
└── logs/
```

`.env` и `logs/` всегда находятся рядом с exe. Каталог данных `data/` можно перенести через
`DATA_DIR`: относительный путь считается от portable-папки, абсолютный используется как указан.

#### Автозапуск

Автозапуск включается вручную и действует для текущего пользователя Windows:

- `Enable-Autostart.cmd` создаёт `ShikiUpdatesBot.lnk` в пользовательской автозагрузке;
- `Disable-Autostart.cmd` удаляет этот ярлык;
- повторный запуск любого помощника безопасен.

Бот запускается после входа этого пользователя в Windows. Консоль остаётся видимой.
После перемещения или переименования portable-папки снова запустите `Enable-Autostart.cmd`.

Без помощников можно нажать `Win+R`, открыть `shell:startup` и создать ярлык вручную. Рабочей папкой
ярлыка должна быть portable-папка.

#### Проверка и обновление

```powershell
.\ShikiUpdatesBot.exe --check-config
.\ShikiUpdatesBot.exe --version
```

Portable-версия для Windows раз в сутки проверяет, появилась ли новая версия. Если опубликована
новая Windows-сборка, владелец один раз получает сообщение. `/info` показывает сведения о боте и его
состоянии, а `/version` позволяет владельцу обновить сведения о версиях вручную.

Для обновления остановите бота и замените только `ShikiUpdatesBot.exe`. Не удаляйте `.env`, `data/`
и `logs/`. Для удаления сначала отключите автозапуск, затем удалите portable-папку.

> Сборка не подписана и может вызвать предупреждение SmartScreen, Smart App Control или антивируса.
> Запуск от администратора не требуется и не рекомендуется. Скачивайте архив со
> [страницы последнего релиза](https://github.com/WorgaNomoR/ShikiUpdatesBot/releases/latest), где

Дополнительная инструкция находится в [README-Windows.txt](README-Windows.txt) и внутри архива.

### Первый запуск в Telegram

Владелец должен хотя бы один раз открыть чат с ботом и отправить `/start`: Telegram не разрешает
боту первым начать диалог. На старте ShikiUpdatesBot проверяет, может ли доставить владельцу
сообщение.
Только после успешной доставки начинается фоновое отслеживание.

Если владелец был недоступен, команды продолжат работать, но фоновая проверка не начнётся. После
восстановления связи владелец может отправить `/start`, чтобы запустить её без перезапуска бота.
Обычный `/start` при этом только открывает главное меню и сам по себе не включает уведомления.

Главный экран ссылается на настроенный профиль Shikimori, объясняет публичные разделы и показывает
примеры поиска. Меню оформлено иллюстрациями, но остаётся доступным и без них.
Кнопка **«Найти тайтл»** открывает поиск в текущем чате для владельца и личных подписчиков;
остальным предлагает подтвердить личную подписку.
Кнопка **«Назад»** возвращает на предыдущую страницу, а
**«Закрыть»** завершает главное меню. Инструменты владельца показываются только владельцу в личном
чате с ботом: сначала идут подбор тайтла из запланированного и рассылка, затем каталог пользователей,
банк дополнительных фактов и резервное копирование. Принудительное обновление сведений о версиях
остаётся доступно кнопкой **«Обновить сведения»** на экране **«О боте»**.

При самом первом успешном запуске бот запоминает текущую историю и избранное без рассылки старых
событий. Уведомления начинаются с последующих изменений.

### Поиск тайтлов из любого чата

Inline-поиск доступен владельцу и активным подписчикам. В поле сообщения любого Telegram-чата
введите username бота, затем один из префиксов и название:

- `anime Берсерк` или `аниме Берсерк`;
- `manga Higurashi` или `манга Когда плачут цикады`;
- `ranobe Re:Zero` или `ранобэ Re:Zero`.

На мобильном экране удобнее короткие префиксы: `а` или `a` для аниме, `м` или `m`
для манги, `р` или `r` для ранобэ. Регистр и повторяющиеся пробелы не имеют значения. Поиск аниме не показывает
музыкальные клипы, проморолики и рекламу, но сохраняет сериалы, фильмы, OVA, ONA и спецвыпуски.

На главном экране кнопка **«Найти тайтл»** подставляет username бота и открывает inline-поиск прямо
в текущем чате. Неподписанному пользователю в личном чате сначала предлагается подтвердить
подписку; из группы кнопка открывает личный чат с ботом для такого подтверждения. Сама группа при
этом не подписывается, а её участники не получают личный доступ к поиску.

После короткой паузы Telegram покажет до 49 тайтлов. На первой непустой странице к ним добавляется
явно обозначенный результат **«Поделиться ShikiUpdatesBot»**: его выбор отправит в чат краткое
описание проекта и ссылку на GitHub с инструкцией по запуску собственного бота. На следующих
страницах длинной выдачи бот при необходимости добавляет результат **«Отправить интересный факт»**.
Подпись заранее предупреждает, что его выбор отправит в чат короткий факт об аниме или Японии.

Выбранный тайтл отправляется как карточка с постером либо как текстовая карточка, если подходящего
постера нет. Для длинной выдачи следующая страница подгружается только при прокрутке списка
результатов. Под каждой отправленной карточкой доступны новый поиск в текущем чате, страница тайтла
на Shikimori и информационный экран **«О боте»**, который не оформляет подписку автоматически.

Если поиск временно недоступен из-за частых запросов, над пустой выдачей появится кнопка с
примерным временем ожидания. Она уже сообщает причину; нажатие необязательно и лишь откроет
в личном чате подробное объяснение и кнопку возврата к поиску.

Неподписанному пользователю поиск предложит открыть личный чат с ботом и подтвердить подписку.
Переход к боту для поиска не включает подписку автоматически: действующему подписчику сразу
доступна кнопка **«Вернуться к поиску»**, а новый пользователь сначала видит подтверждение. Эта
кнопка вручную открывает выбор чата и подставляет username бота; подписка сама не запускает поиск и
ничего не отправляет в другие чаты. Подписка группового или канального чата не открывает
inline-поиск его участникам, а блокировка или отписка действует со следующего запроса.

### Команды

| Команда | Что происходит |
|---|---|
| `/start` | Открывает главное меню; для владельца также возобновляет остановившееся отслеживание |
| `/stop` | Открывает подтверждение отписки от уведомлений |
| `/status` | Показывает, что пользователь смотрит и читает сейчас |
| `/stats` | Открывает выбор статистики за текущий квартал или всё время |
| `/stats all` | Сразу показывает статистику за всё время |
| `/lists` | Показывает аниме, мангу и ранобэ с выбором конкретного статуса или всего списка |
| `/favs` | Показывает избранные аниме, мангу, ранобэ, персонажей и людей индустрии |
| `/fact` | Показывает интересный факт об аниме или Японии |
| `/facts` | Управляет дополнительным банком фактов *(владелец)* |
| `/pick` | Помогает выбрать аниме, мангу или ранобэ из списка «Запланировано» *(владелец)* |
| `/info` | Показывает информацию о боте, его версии и состоянии |
| `/broadcast` | Отправляет сообщение всем подписчикам *(владелец)* |
| `/block ID` | Закрывает пользователю доступ к боту и удаляет его из подписчиков *(владелец)* |
| `/unblock ID` | Снимает блокировку, но не восстанавливает подписку *(владелец)* |
| `/blocklist` | Показывает всех заблокированных пользователей (Telegram ID — в порядке возрастания) *(владелец)* |
| `/useralerts on\|off` | Включает или отключает уведомления владельцу о новых пользователях *(владелец)* |
| `/cancel` | Отменяет команду, ожидающую следующего действия владельца: бэкап, рассылку, загрузку фактов и другие операции *(владелец)* |
| `/subs` | Показывает подписчиков: ссылка на профиль зависит от настроек приватности Telegram, числовой ID всегда виден и доступен для копирования *(владелец)* |
| `/users` | Показывает единый каталог подписчиков, заблокированных и других зарегистрированных пользователей *(владелец)* |
| `/backup` | Открывает резервное копирование и восстановление данных *(владелец)* |
| `/version` | Обновляет и показывает сведения о версиях *(владелец)* |

В списке команд Telegram виден только `/start`. Остальные команды из таблицы можно отправить
напрямую.

Подписка влияет только на автоматические уведомления и доступ к inline-поиску. `/status`, `/stats`,
`/lists`, `/favs`, `/fact`, `/info` и соответствующие кнопки главного меню доступны независимо от
неё. Подписка и отписка от уведомлений выполняются только после явного подтверждения.

`/fact` присылает интересный факт об аниме или Японии. Кнопка **«Ещё факт»** заменяет его новым
в том же сообщении, а **«Поделиться»** позволяет выбрать чат и отправить  этот факт друзьям.

Команда владельца `/facts` показывает количество встроенных и дополнительных фактов и
состояние загруженного файла. Через неё можно загрузить новый `facts.json`, проверить предпросмотр
добавленных, изменённых и удалённых записей, применить или отменить полную замену, скачать текущий
файл и закрыть меню. Если дополнительных фактов пока нет, вместо пустого файла бот
предлагает готовый пример из пяти фактов. Очистка выполняется ровно двумя кнопками:
**«Очистить дополнительные»** → кнопка **«Да, удалить…»** с точным числом удаляемых фактов; встроенный банк при этом не меняется. [Формат файла, ограничения и готовый
пример](#дополнительный-банк-фактов-factsjson) находятся в техническом справочнике ниже.
Новый банк становится доступен через `/fact`, **«Ещё факт»** и inline-отправку сразу, без перезапуска.

Команда владельца `/pick` помогает решить, что посмотреть или почитать из списка
«Запланировано». После выбора **аниме**, **манги** или **ранобэ** бот предлагает случайный тайтл.
**«Ещё вариант»** не повторяет уже показанное, пока не закончатся все варианты в категории, а
**«Что-нибудь совсем другое»** старается предложить максимально непохожий вариант — из другого
десятилетия и с другими жанрами.
Тайтлы, которые пока только анонсированы, в выборе не участвуют.

Команда использует последние сохранённые данные и показывает время их обновления, не запуская новое
обновление списка. Если подходящих вариантов нет или данные пока недоступны, бот сообщит об этом
прямо в меню. Закрыть меню можно кнопкой или командой `/cancel`.

Inline-поиск вызывается через username бота в поле сообщения и поэтому не отображается в меню `/`.
Например, замените `@your_shiki_bot` на username своего бота, введите
`@your_shiki_bot anime Берсерк`, выберите карточку и отправьте её в текущий чат.

`/broadcast` принимает текст, фото, видео, GIF, стикер, документ или голосовое сообщение. Перед
рассылкой бот показывает владельцу такое же превью, какое получат подписчики, и просит подтвердить
отправку. `/cancel` отменяет операцию до подтверждения.

`/block` сразу закрывает пользователю доступ ко всем функциям бота, удаляет его из подписчиков и
отключает уже отправленные ему кнопки. Можно заранее указать числовой Telegram ID человека, который
ещё не обращался к боту. `/unblock` возвращает доступ, но подписаться снова пользователь должен
самостоятельно. `/blocklist` показывает владельцу количество заблокированных пользователей и их
числовые Telegram ID, каждый из которых можно скопировать. Владелец бота не может заблокировать сам себя.

Бот отдельно запоминает пользователей при первом обращении через поддерживаемую команду или кнопку.
Владелец получает одно уведомление о новом пользователе. Эти уведомления по умолчанию включены.
Владелец может отключить их командой `/useralerts off` и включить снова через `/useralerts on`.
Бот продолжает запоминать новых пользователей при отключённых уведомлениях. После включения
пропущенные сообщения не отправляются.

Команда владельца `/users` доступна только в личном чате с ботом и объединяет подписчиков,
заблокированных и остальных зарегистрированных пользователей в одном каталоге. Счётчик охватывает
только пользователей, запомненных после включения этого учёта: более ранние подписчики и заранее
заблокированные ID не выдаются за полную историческую аудиторию. Подписки групп и каналов остаются
видны отдельно и не увеличивают этот счётчик. Имя и username указаны на момент первого обращения
и могут отличаться от нынешних.

### Статистика, отчёты и избранное

`/stats` предлагает два отчёта:

- **за текущий квартал** — по событиям истории за этот период;
- **за всё время** — по всем тайтлам в открытых списках Shikimori.

Квартальный отчёт автоматически приходит владельцу 1 января, апреля, июля и октября. В нём есть
итоги, сравнение с прошлым кварталом и достижения. Кварталы отсчитываются по времени UTC.

После простоя бот сначала проверит пропущенную историю, затем пришлёт отчёты за пропущенные
кварталы по очереди. Текущая статистика при этом показывает нынешний квартал.
Поздние изменения прошлых кварталов появятся отдельной поправкой в следующем новом отчёте.
Прежние отчёты сохранятся.

Если возникает проблема с данными квартала, бот сообщает владельцу и сохраняет накопленную
историю. Уведомления о новых событиях истории возобновятся после устранения проблемы или
восстановления через `/backup`.

Если отправка прервалась, бот продолжит тот же отчёт автоматически. После сбоя последняя часть
иногда может повториться.

Во всех отчётах манга и ранобэ показаны отдельно, а тайтлы с неизвестным типом — в разделе
**«Не определено»**. Если для разделения прошлого квартала не хватает данных, сравнение
показывает общий итог с пояснением.

Статистика включает завершённое, брошенное и запланированное, оценки, жанры, темы, аудиторию,
студии, издателей, источники адаптации, годы и возрастные рейтинги. Она также показывает примерное
время просмотра, число прочитанных глав и томов, а также сравнение личных оценок со средним рейтингом
Shikimori.

Квартальная статистика может быть неполной: бот видит только доступную историю Shikimori.
События без надёжной даты не входят в итоги; о таких пропусках бот предупреждает в отчёте.
Если бот начал работу в середине квартала, в отчёте указана дата начала сбора.
При обновлении ранее накопленные данные сохраняются без пересчёта.

В статистике за всё время у аниме, манги и ранобэ есть свёрнутый блок «Интересное»:
для аниме это сериал с наибольшим известным числом эпизодов и самый длинный фильм;
для манги и ранобэ — тайтлы с наибольшим числом прочитанных глав и томов.
В каждой категории также показываются самый старый и самый новый завершённые тайтлы.
Все перечисленные рекорды считаются только среди завершённых тайтлов.
Показываются только результаты, для которых в текущем списке есть достоверные данные.

`/favs` показывает избранное со ссылками и оценками, если они есть. Пустые категории не выводятся.

`/lists` доступна всем, даже без подписки. В ней можно выбрать аниме, мангу или ранобэ и посмотреть
тайтлы с конкретным статусом — например, завершённые или запланированные, — либо открыть весь
список с разбивкой по статусам. Раздел **«Всё вместе»** показывает все категории отдельно, включая
тайтлы, тип или статус которых пока не удалось определить. В каждом разделе есть счётчик тайтлов и
непустых статусов, а длинные блоки статусов можно свернуть и быстро вернуться к началу отчёта.
Большой список автоматически приходит несколькими последовательными сообщениями.
При выборе списка в главном меню или через `/lists` бот показывает «⏳ Формирую и отправляю
список…» до завершения отправки, затем убирает этот статус.

Тайтлы показаны в нумерованных компактных карточках: в первой строке видны название и оценка автора
профиля, а остальные сведения разнесены по коротким смысловым строкам. Комментарий показывается
курсивом непосредственно под соответствующей карточкой. Внутри каждого статуса сначала идут тайтлы
с более высокой оценкой автора профиля, затем остальные по названию.
Если данные ещё не готовы или повреждены, бот прямо сообщит об этом.

Техническое описание источников данных и сетевого поведения команд находится в разделе
[«Хранение данных и жизненный цикл»](#хранение-данных-и-жизненный-цикл).

### Резервное копирование и перенос

`/backup` открывает две операции:

- **Экспорт** присылает ZIP с подписчиками, статистикой, дополнительными фактами и другими данными, необходимыми для
  восстановления бота.
- **Импорт** восстанавливает список блокировок, подписчиков, дополнительные факты и статистику
  текущего и завершённых кварталов. Остальные необходимые данные бот создаёт заново.

Для переноса на другой компьютер или хостинг:

1. В старом боте выполните `/backup` → **Экспорт** и сохраните ZIP.
2. Полностью остановите бота на старом месте.
3. Запустите бота на новом месте, выполните `/backup` → **Импорт** и отправьте ZIP как документ.
4. Проверьте подписчиков, статистику и работу команд до удаления старых файлов.

> [!CAUTION]
> Никогда не запускайте одновременно две копии бота с одним `BOT_TOKEN`. Они начнут конфликтовать
> при получении команд из Telegram, поэтому команды и уведомления будут работать нестабильно.

Кроме ручного экспорта, бот автоматически отправляет владельцу архивы с тегом `#backup`: при
накопленных изменениях подписок, при смене квартала и как еженедельную страховку. Подписки и
отписки сохраняются сразу, но связанные с ними архивы уходят не чаще одного раза за 24 часа;
несколько изменений за это время объединяются в одну копию с общими количествами. После временной
ошибки бот повторит отправку позже. При запуске на хостинге, через Python или Docker бот
дополнительно пытается отправить финальный архив перед обычной остановкой. При закрытии
portable-версии для Windows такой архив не отправляется.

Telegram-бэкапы помогают восстановиться, но не заменяют постоянный диск на хостинге. Точные правила
и ограничения импорта описаны в [техническом справочнике](#бэкап-и-восстановление).

### Ограничения и частые проблемы

- **Бот молчит после запуска.** Владелец должен открыть диалог и отправить `/start`. Проверьте также
  токен бота, данные владельца в настройках, соединение и [логи](#ошибки-и-диагностика).
- **Локальный бот отвечает только после включения компьютера.** Это ожидаемо: во время сна или
  выключения бот не работает. Для ожидаемой доступности 24/7 используйте хостинг или сервер.
- **Сообщения Telegram задерживаются или не приходят.** Проверьте доступность Telegram из сети, где
  запущен бот. Ограничения в России могут мешать соединению с Telegram.
- **После простоя пришло много сообщений.** Бот присылает недавние изменения, найденные за время
  перерыва.
- **Статистика текущего квартала неполная.** Проверьте пояснения в самом отчёте. Причины пропусков
  описаны в разделе [о статистике](#статистика-отчёты-и-избранное).
- **Portable-версия не запускается второй раз.** В одной portable-папке разрешена только одна копия
  бота.
- **Хостинг потерял данные после повторного развёртывания.** Проверьте подключение постоянного диска и
  восстановите последний Telegram-бэкап.
- **Профиль Shikimori закрыт.** Зайдите в настройки Shikimori, откройте раздел **«Профиль»** и в
  пункте **«Могут видеть мой список»** выберите **«Все посетители сайта»**. Бот также пришлёт
  владельцу готовую ссылку на страницу настроек.
- **Shikimori временно недоступен.** Бот пропустит неудачную проверку и повторит её позже; локальные
  `/stats` и `/favs` продолжат работать.

## Технический справочник

### Хостинг из GitHub-репозитория

Этот вариант даёт ожидаемую работу 24/7 без домашнего компьютера, если выбранный тариф не засыпает,
платформа сохраняет диск и имеет стабильный доступ к Telegram и Shikimori.

Общая схема для платформ, которые собирают приложение по `Dockerfile`:

1. Сделайте fork репозитория в свой GitHub-аккаунт.
2. Создайте проект на хостинг-платформе и подключите fork.
3. В разделе **Environment Variables** (переменные окружения) добавьте `BOT_TOKEN`, `OWNER_ID` и
   `SHIKI_USER`.
4. Если платформа запрашивает Healthcheck Path, укажите `/health`.
5. Подключите постоянный диск (volume) к `/data`. Если платформа предоставляет для него другой путь,
   добавьте переменную окружения `DATA_DIR` с этим путём.
6. Проверьте логи запуска и от имени владельца отправьте `/start` в Telegram.

> [!WARNING]
> Без постоянного диска каталог `/data` обычно временный. Подписчики, статистика и квартальные
> данные могут исчезнуть после повторного развёртывания. Telegram-бэкапы — страховка, а не замена
> правильно подключённому постоянному диску.

Заранее проверьте непрерывность работы тарифа, поддержку постоянного диска, исходящий трафик,
сетевой доступ к Telegram, способ оплаты и правила автоматического перезапуска.

[Railway](https://docs.railway.com/volumes/reference) позволяет подключить постоянный диск к
выбранному пути, в том числе `/data`. На бесплатном тарифе новые развёртывания
[недоступны в региональные часы пик](https://docs.railway.com/deployments/reference#free-tier-peak-hours-restriction),
поэтому первый запуск или обновление иногда приходится отложить. [Bothost](https://bothost.ru/docs/)
использует `/app/data` для постоянных данных; для него добавьте переменную окружения
`DATA_DIR=/app/data` и выберите тариф с постоянным диском. Платформа только с временным диском не
подходит без отдельного постоянного хранилища.

`/health` — служебный веб-адрес, а не команда Telegram. Он позволяет хостингу проверять, продолжает
ли бот работать. Автоматический перезапуск сработает только на платформе, которая регулярно
проверяет этот адрес и настроена реагировать на ошибку. Подробности находятся в разделе
[«Healthcheck и ответственность за перезапуск»](#healthcheck-и-ответственность-за-перезапуск).

### Запуск через Python

Для запуска понадобятся Git, терминал и Python 3.12, на котором проект разрабатывается и
автоматически проверяется. На других версиях Python он может работать, но проект их не проверяет:
совместимость придётся оценивать самостоятельно.

```bash
# 1. Клонировать репозиторий
git clone https://github.com/WorgaNomoR/ShikiUpdatesBot.git
cd ShikiUpdatesBot

# 2. Создать .env из примера и заполнить обязательные значения
cp .env.example .env

# 3. Установить зависимости
pip install -r requirements.txt

# 4. Запустить из корня репозитория
python main.py
```

`.env` читается из корня приложения с UTF-8 BOM или без него. Уже заданные переменные процесса имеют
приоритет и не перезаписываются значениями из файла.

В PowerShell вместо `cp .env.example .env` используйте `Copy-Item .env.example .env`.

При запуске из исходников по умолчанию используется `/data`. Если этот путь не подходит или
недоступен для записи, задайте в `.env` подходящий `DATA_DIR`, например абсолютный путь или
`DATA_DIR=./data`.

При запуске из исходников доступны healthcheck и финальный бэкап перед обычной остановкой.
При таком запуске `/info` показывает режим `Python/source или Docker`. Бот раз в сутки обновляет
сведения о доступных версиях, а владелец может сделать это вручную командой `/version`. Исходники
обновляются через Git.

Процесс остановится вместе с терминалом, компьютером или пользовательской сессией. Для постоянной
работы настройте автоматический запуск и перезапуск средствами операционной системы либо используйте
хостинг или Docker.

### Запуск через Docker Compose

Понадобятся Git, Docker и Docker Compose. Выполните команды в терминале:

```bash
# 1. Клонировать репозиторий
git clone https://github.com/WorgaNomoR/ShikiUpdatesBot.git
cd ShikiUpdatesBot

# 2. Скопировать настройки и заполнить BOT_TOKEN, OWNER_ID и SHIKI_USER
cp .env.example .env

# 3. Собрать и запустить
docker compose up -d --build

# 4. Смотреть логи
docker compose logs -f

# 5. Остановить
docker compose down
```

Для обновления исходников после `git pull`:

```bash
docker compose up -d --build
```

Compose передаёт все значения из `.env`, но намеренно фиксирует `DATA_DIR=/data` и монтирует туда
локальную папку `./data`. Значение `DATA_DIR` из `.env` не может перенаправить данные из этой папки.

Контейнер имеет `restart: unless-stopped`: Docker перезапустит завершившийся контейнер, если он не
был остановлен вручную. Это не означает автоматический перезапуск процесса, который продолжает
работать, но отдаёт `503` на `/health`. Для такой реакции нужен внешний мониторинг или оркестратор с
явной политикой восстановления.

Порт по умолчанию не публикуется на хост. Если healthcheck должен быть доступен снаружи контейнера,
добавьте в сервис:

```yaml
    ports:
      - "8080:8080"
```

При другом `PORT` справа указывается внутренний порт. Например, для `PORT=9090` подходит
`"8080:9090"`: внешний порт останется `8080`, внутренний станет `9090`.

### Конфигурация

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `BOT_TOKEN` | Да | — | Токен Telegram-бота от BotFather |
| `OWNER_ID` | Да | — | Числовой Telegram ID владельца |
| `SHIKI_USER` | Да | — | Ник отслеживаемого пользователя Shikimori |
| `DISPLAY_NAME` | Нет | Значение `SHIKI_USER` | Имя пользователя в сообщениях |
| `DISPLAY_NAME_GENDER` | Нет | `auto` | Режим грамматики: `auto`, `male`, `female` или `none` |
| `SHIKI_BASE_URL` | Нет | `https://shikimori.io` | Домен Shikimori или совместимого зеркала |
| `CHECK_INTERVAL` | Нет | `900` (15 мин.) | Интервал проверки истории и избранного в секундах |
| `ERROR_NOTIFY_INTERVAL` | Нет | `1800` (30 мин.) | Минимальный интервал уведомлений владельцу об ошибках |
| `FULL_SYNC_INTERVAL` | Нет | `21600` (6 ч.) | Интервал полной синхронизации статистики в секундах |
| `DATA_DIR` | Нет | `/data`; в portable-версии — `data/` | Каталог данных бота |
| `PORT` | Нет | `8080` | Порт healthcheck в Python/Docker; portable-версия его игнорирует |

Пустые `BOT_TOKEN`, `OWNER_ID` и `SHIKI_USER` останавливают запуск с понятной ошибкой. `OWNER_ID` и
интервалы должны быть целыми числами.

`DISPLAY_NAME` автоматически склоняется только для поддерживаемых русских имён из кириллических
букв и необязательных дефисов. Пробелы, латиница, цифры, подчёркивания, эмодзи и другая пунктуация
оставляют имя без изменений.

`DISPLAY_NAME_GENDER=auto` пытается определить пол по поддерживаемому русскому имени. `male` и
`female` всегда выбирают мужскую или женскую грамматику сообщений. Поддерживаемое русское имя при
этом склоняется с выбранным полом, в том числе неоднозначные имена вроде `Саша` и `Женя`; латинское
или иное неподдерживаемое имя остаётся неизменным во всех падежах. `none` отключает склонение и
оставляет мужские варианты. Ошибка распознавания или склонения не мешает запуску: имя остаётся
неизменным, а явно выбранный пол сообщений сохраняется. Контекст имени создаётся один раз при
запуске, поэтому изменение этих настроек требует перезапуска бота.

### Хранение данных и жизненный цикл

В `DATA_DIR` хранятся:

- `quarters/` — снимки завершённых кварталов;
- `seen_favourites.json` — уже обработанное избранное;
- `event_journal.json` — принятая история и незавершённый сбор;
- `notification_progress.json` — очередь уведомлений, отметки обработки и результат доставки каждому получателю;
- `seen_ids.json` — копия принятых ID истории для просмотра;
- `stats_all.json` — тайтлы и агрегаты за всё время;
- `stats_current.json` — проекции исходных кварталов, явные корректировки, отметка обработки и состояние доставки квартального отчёта;
- `blocked_users.json` — глобально заблокированные Telegram user ID;
- `known_users.json` — ID пользователя, его имя и username на момент первого обращения, а также время этого обращения;
- `user_alerts.json` — настройка уведомлений владельцу о новых пользователях;
- `subscribers.json` — подписчики, идентичность каждой подписки и расписание автоматических бэкапов;
- `update_state.json` — сведения о доступных версиях;
- `facts.json` — только дополнительные факты владельца;

Эти файлы не нужно коммитить: они уже исключены через `.gitignore`. Запись JSON выполняется через
временный файл и атомарную замену, чтобы незавершённая запись не повредила опубликованный файл.

Прежний формат журнала читается без повторной рассылки. При первом возобновлении обработки
бот переводит его в новый формат, сохраняя прежние записи и отметки обработки.
Для отката к версии до v1.4.0 нужна резервная копия, сделанная до перехода: прежние версии
не читают новый формат журнала.
Для отката после перехода на v1.5.0 также нужна копия до обновления: прежние версии не поддерживают
новую квартальную статистику и планы отчётов с корректировками.
После перехода на v1.6.0 для отката также нужна копия до обновления: прежние версии не читают
журнал с очередью уведомлений. Уже обработанная история переносится без массовой рассылки.
После перехода на v1.7.0 для отката к v1.6.0 также потребуется копия до обновления:
завершённые уведомления получают новый формат кратких итогов.
После перехода на v1.8.0 для отката к v1.7.0 нужна копия до обновления:
бот может удалить завершённое начало очереди, сохранив отдельную отметку завершения.
После перехода на v1.8.2 попытки доставки сохраняются отдельно от истории. Для отката к прежней
версии нужна копия до обновления: старые версии не читают разделённый формат. Перенос сохраняет
очередь, сообщения, получателей, попытки и сроки без повторной рассылки обработанной истории.
Одно прежнее незавершённое событие обрабатывается; если его успели отправить до обновления, возможен дубль.
При обновлении бот тихо переносит ранее известные ID истории в журнал, не рассылая старые события
и не создавая для них выдуманные записи. Если прежний кеш отсутствует или повреждён, бот запоминает
одну страницу истории без рассылки; успешная пустая страница тоже завершает инициализацию. После
этого `seen_ids.json` служит только копией для просмотра: его повреждение или ошибка записи не
сбрасывают исправный журнал. Кеш избранного `seen_favourites.json` по-прежнему можно тихо собрать
заново; повреждённый файл не перезаписывается при чтении.

Если журнал, его связь с кварталом или данные квартала недоступны, бот сохраняет файлы и сообщает
владельцу о проблеме. Обработка истории приостанавливается, а восстановление через `/backup`
остаётся доступным. Удаление ранее привязанного журнала не считается первым запуском.
Если проблема только в истории, уведомления об избранном, обновление списков и автоматические
бэкапы продолжаются; смена квартала ждёт восстановления обработки истории.

Журнал сохраняет принятые события, включая пропущенные уведомлениями служебные записи. Исходное
время хранится без изменений; перевод в UTC возможен только при явно указанном часовом поясе.
Статистика новых событий относится к исходному кварталу по UTC. Время без часового пояса,
отсутствующая или неверная дата, а также дата позже первого наблюдения не заменяются временем
проверки и не распределяются по кварталам. Отчёт явно показывает количество таких событий.
Такая запись впоследствии не становится достоверной автоматически.

При обновлении сохраняется накопленная статистика по прежним правилам. Уже применённая история
не пересчитывается и не рассылается повторно. Данные, закрытые до обновления, остаются неполными:
позднее дополнение не выдаётся за восстановленный полный итог. `by_quarter` сохраняет прежнюю
сводку такого периода, а известную новую часть записывает отдельно как `event_time_partial`.
Незавершённый сбор истории в статистику не попадает. Снимки и новые отчёты явно сохраняют
неполноту доступной истории; сегодняшние списки не доказывают состояние тайтлов в прошлом.

Ошибочные данные о названии или ссылке в ответе Shikimori не останавливают приём следующих событий:
бот использует название `???` или убирает ссылку. Если вид тайтла отсутствует или передан
в неверном формате, событие сохраняется без уведомления.

При занятом бюджете журнала от 6 МиБ владелец получает предупреждение: учитываются история,
очередь и резерв всех оставшихся попыток и итогов доставки. Поэтому при большой ожидающей очереди
предупреждение приходит раньше, чем файлы достигнут 6 МиБ. Общий прежний бюджет содержимого остаётся 8 МиБ с отдельным
резервом 4 КиБ для отметок обработки. Продолжение сбора или приём набора, который не помещается, откладывается
с сохранением данных для обработки и незавершённого сбора. Завершённое начало истории постепенно
сжимается: остаются точные ID и исходные данные, нужные для статистики и поздних событий.
Ожидающие уведомления сохраняются полностью. Сохраняй резервные копии для восстановления.

Полностью завершённое начало очереди автоматически удаляется вместе с краткими итогами.
Отдельная отметка сохраняет границу завершения, чтобы эти уведомления больше не отправлялись
и не получали новых подписчиков. Удалённые итоги недоступны: завершение не означает успешную
доставку и не доказывает, что сообщение не было принято. История событий и основания статистики
сохраняются. Если хотя бы один получатель ещё ожидает отправки, всё уведомление сохраняется
целиком с прежним текстом, получателями, попытками и сроками; удаление останавливается перед ним.
Завершённые уведомления за ним могут временно храниться как краткие итоги доставки, отмены,
истечения срока или постоянного отказа, с сохранением возможности принятия сообщения и дублей.

Обслуживание доступно и когда новое уведомление не помещается после обновления статистики.
После освобождения места бот продолжит его подготовку без повторного учёта события. Очистка и сжатие
выполняются ограниченными порциями; если места всё ещё недостаточно, обработка останется
отложенной, а сохранённые уведомления и резервные копии продолжат обслуживаться. Обслуживание очереди
не освобождает место в данных квартальной статистики, если заполнены они.

Ёмкость зависит от длины истории и уведомлений, числа получателей и количества попыток.
Резерв теперь рассчитывается по верхней границе возможного роста, включая ещё не подтверждённую
последнюю попытку и любой допустимый итог. Все шесть попыток и срок 72 часа сохраняются.
Для записи истории 494 байта, уведомления 500 байт UTF-8, девятизначных номеров чатов
и времени постановки `1000` повторяемая проба штатным форматом дала такие результаты:

| Получателей на событие | Фактические байты одного события с очередью | Резерв будущего роста | Свежих событий до изменения | После изменения |
|---|---:|---:|---:|---:|
| 20 | 5 470 | 8 820 | 311 | 599 |
| 100 | 21 550 | 44 100 | 64 | 128 |
| 500 | 101 950 | 220 500 | 12 | 26 |
| 1000 | 202 450 | 441 000 | 6 | 13 |
| 7000 | 1 408 450 | 3 087 000 | 0 | 1 |

В этом примере начальный резерв одного ожидающего получателя — 441 байт вместо 1088.
Одно событие для 7000 получателей занимает с резервом 4 495 450 байт при прежнем бюджете 8 МиБ.
Перед обновлением сделай бэкап: прежняя версия может отклонить большую очередь,
которая стала помещаться благодаря новому расчёту. Для отката используй копию до обновления.
Десять ожидающих событий для 1000 получателей занимают с резервом 6 431 787 байт;
для 7000 получателей десять таких событий по-прежнему не помещаются.
Это синтетический ориентир почти пустого журнала, который не гарантирует публичную нагрузку:
длинные сообщения, другие времена, накопленная история и незавершённый сбор меняют доступный запас.
Расчёт резервирует верхнюю границу, а фактические попытки расходуют её постепенно;
уменьшение резерва при обработке не увеличивает уже принятый бюджет.
После удаления завершённого начала очереди остаются записи истории и одна отметка завершения.
Полные записи завершённого начала истории заменяются компактными исходными данными. Точные ID
не удаляются: старое событие не будет принято снова, а позднее новое событие попадёт в прежний
порядок статистики. Очистка останавливается перед ожидающим уведомлением. Рост продолжается за счёт
ID, новых тайтлов и кварталов, ожидающей очереди и накопленной статистики.
Квартальные снимки сохраняются без автоматической очистки. Экспорт резервной копии не освобождает место.

Обновление на версию с компактной историей проходит без повторного учёта и рассылки старых событий.
Обычно сжатие начинается при накоплении 512 КиБ полных записей и удаляет не больше 128 записей
за один проход; при нехватке места бот пробует освободить завершённое начало и ниже этого порога.
Если есть ожидающие получатели или выросли сами ID и статистика, сжатия может быть недостаточно.
Новый формат `event_journal.json` v5 требует соответствующие `notification_progress.json`
и `stats_current.json` для восстановления. Старые полные архивы и старые квартальные архивы
поддерживаются; откат на прежнюю программу требует резервной копии, сделанной до обновления.
Прежняя программа не читает компактный формат.

Сжатие исходных записей не уменьшало очередь, статистику или снимки. ZIP в этих пробах вырос:

Ограничения остаются 8 МиБ на файл, 32 МиБ до сжатия, 20 МиБ ZIP и 256 элементов архива.
Физические файлы истории/очереди имеют дополнительный небольшой общий заголовок;
их суммарный размер отличается от логического журнала.

снимки в этой пробе не менялись, поскольку новой ротации не было. Следующая ротация добавит снимок.
Длинные сообщения, новые кварталы, большие ID, незавершённый сбор и другие данные меняют запас.
Сжатие освобождает место для дальнейшей обработки, но не обеспечивает бесконечное хранение.

Скорость отправки и пределы хранения различны: обслуживание остаётся по 20 попыток за порцию,
с минутным интервалом при ожидающей очереди. Для 7000 первых попыток нужны 350 порций,
около 5 часов 50 минут даже при идеальном обслуживании; повторы, длительность запросов и другие
обязанности бота увеличивают время. Эти оценки не являются измерением скорости Telegram.

Сохранение попытки и её результата больше не переписывает накопленную историю. Уже проверенная
очередь повторно используется, пока её сохранённое состояние не изменилось; для одного получателя
копируется только изменяемая часть. Изменение, отсутствие или повреждение файлов требует новой полной
проверки; восстановление из бэкапа также отменяет прежнее состояние в памяти.
Каждое новое сохранение по-прежнему проверяет и записывает очередь целиком, поэтому затраты зависят
от числа ожидающих уведомлений и получателей. Эти изменения не увеличивают лимиты и не гарантируют
скорость рассылки для большой аудитории. Копируй оба файла
вместе с `stats_current.json`; ручной и автоматический бэкап включают их согласованно.

#### Дополнительный банк фактов facts.json

Встроенные 50 общих и 6 выбранных владельцем фактов всегда остаются в программе. Дополнительный
`facts.json` имеет версионированный формат. [Готовый пример с пятью фактами](examples/facts.json)
можно скачать без подготовки: файл уже называется `facts.json` и целиком проходит ту же проверку,
что и загрузка через Telegram. При загрузке имя может быть любым — бот принимает документы с
расширением `.json`, проверяет содержимое и сам сохраняет канонический `facts.json`.

```json
{
  "schema_version": 1,
  "bank_version": "2026-09",
  "facts": [
    {
      "id": "anime-example",
      "text": "Текст дополнительного факта."
    }
  ]
}
```

`id` состоит из строчных латинских букв, цифр и внутренних дефисов, остаётся стабильным и не
повторяет встроенные ID. `text` — обычный текст без HTML; бот сам безопасно оформляет его при
отправке. Файл не может назначить отметку выбора владельца. Ограничения одного файла: 512 КиБ,
до 500 фактов, до 32 символов в ID и до 1000 символов в тексте. Для непустого банка требуется
`bank_version`; канонический пустой банк использует `null`. Если файл отсутствует, не читается или
повреждён, публичные факты продолжают работать на встроенном банке, а `/facts` показывает проблему.

Portable-версия для Windows хранит `.env` и каталог `logs/` рядом с собой, а данные — в `data/` или
явно заданном `DATA_DIR`. Логи ограничены по размеру и не входят в `/backup`. Именованный Windows
mutex разрешает только одну копию бота из одной portable-папки; отдельные папки технически
независимы.

При запуске через Python или Docker по умолчанию используется `/data`. Compose сохраняет его в
`./data`. На хостинге этот путь должен быть подключён к постоянному диску.

При первом запуске история ограничивается одной страницей и становится исходной отметкой без
уведомлений. При последующей проверке бот запрашивает максимум пять страниц за цикл. Если история
длиннее, незавершённый сбор сохраняется и продолжается в следующих циклах, в том числе после
перезапуска. Бот перепроверяет пересечения страниц и начало выдачи, чтобы сдвиг страниц не был
ошибочно принят за завершение. Если пересечение потеряно, проход начинается заново с сохранением
уже собранных записей; постоянные изменения выдачи могут отложить завершение.

До подтверждения известной границы или конца выдачи новые события этого набора не попадают
в статистику и рассылку. Сначала бот сохраняет полный принятый набор, затем обрабатывает его
по очереди. Прерванная обработка возобновляется из локального журнала, даже если эти события уже
исчезли из выдачи Shikimori. Смена квартала ждёт завершения сбора и обработки; избранное,
обновление списков и автоматические бэкапы продолжаются. Бэкапы сохраняют и незавершённый сбор.
Восстановить записи, которые бот не успел получить и которых уже нет у Shikimori, невозможно.

Для принятых событий истории бот заранее сохраняет точное сообщение и состав получателей,
включая подписанные группы. Результат отправки хранится отдельно для каждого чата. Успешно
подтверждённые получатели после перезапуска не получают сообщение повторно. Неудача одного чата
не задерживает сбор истории, статистику и отправку другим; события одного чата идут по очереди.

Для одного сообщения одному получателю допускается до шести сохранённых попыток и до 72 часов
с момента создания очереди, независимо от возраста события у Shikimori. Перезапуск не обнуляет
эти ограничения. Пока есть ожидающие получатели, очередь обслуживается раз в минуту во время паузы
между проверками истории. Повторы сохраняют задержки от минуты до шести часов. Одна порция допускает
до 20 отправок с бюджетом 20 секунд на начало запросов. Если осталось
меньше 10 секунд, новая попытка ждёт следующей порции и не расходуется. Начатый Telegram-запрос
получает полные 10 секунд; ожидание доступа к сохранённым данным и фиксация результата могут
добавить время сверх бюджета порции и не сокращают срок ответа Telegram.
Время отправки учитывается в паузе перед следующей проверкой истории; начатая порция может закончиться позже.
Сбор истории, обновление списков, отчёты и бэкапы выполняются последовательно с этой отправкой,
поэтому длительная работа откладывает обслуживание очереди. Когда ожидающих получателей нет,
бот ждёт следующей обычной проверки; восстановленная в этой паузе очередь также возобновится тогда.
При стандартном интервале истории 15 минут теоретический потолок вырос с 1920 до 28800 попыток
в сутки. Реальная скорость ниже и зависит от Telegram, размера сохранённых данных и остальных задач;
эти числа не гарантируют доставку всей аудитории до истечения 72 часов.
Успех, отмена, истечение ограничений и постоянный отказ сохраняются явно; неподтверждённое сообщение
не считается доставленным. Итоги истёкших и отклонённых записей остаются в журнале и логах;
возможное принятие сообщения до такого исхода сохраняется и после сжатия.

Отписка отменяет прежнюю очередь, повторная подписка её не возобновляет. Новые подписчики получают
только события, очередь которых сформирована после их подписки. Заблокированные и недоступные
чаты удаляются из подписчиков. Перед каждой отправкой бот проверяет актуальную подписку и блокировку.
Если Telegram принял сообщение, но подтверждение потерялось или не сохранилось, повтор может дать
дубль; поздний отказ этого не опровергает. Статистика события повторно не применяется.

`/stats`, `/lists`, `/favs` и `/info` используют уже подготовленные сведения и не зависят от
доступности Shikimori в момент запроса.
`/status`, напротив, получает текущие данные из сети. Успешный результат `/status` повторно
используется для всех чатов в течение минуты, чтобы не создавать лишнюю нагрузку на Shikimori.
Ответ о закрытом профиле успешным результатом не считается и в этот кеш не попадает.
Непустой результат оформляется как структурированный Rich-отчёт; если этот способ доставки
недоступен, бот сохраняет полный обычный текст со всеми тайтлами и ссылками. Заголовок каждой
группы сразу показывает количество тайтлов. До трёх обложек могут дополнять каждую непустую
группу просмотров и чтения только из уже собранных локальных данных: их отсутствие никогда не
скрывает тайтл и не вызывает отдельный запрос к Shikimori.

> [!IMPORTANT]
> Версии до `v0.2.5` могли ошибочно принять запись о прогрессе за завершение. Уже сохранённую ложную
> запись нельзя исправить автоматически, потому что `stats_current.json` не содержит исходного
> описания Shikimori.

### Бэкап и восстановление

Экспорт архивирует весь `DATA_DIR`, кроме временных файлов `*.tmp` и незавершённых каталогов
восстановления `.restore-*.tmp`. Состав файлов фиксируется в начале операции, а восстанавливаемые
JSON копируются как один согласованный снимок. Чтение и сжатие выполняются в фоне, поэтому бот
остаётся отзывчивым во время подготовки архива.

Экспорт безопасно отменяется до отправки в Telegram, если в снимке больше 256 файлов,
восстанавливаемый файл больше 8 МиБ, суммарный несжатый объём больше 32 МиБ или готовый ZIP больше
20 МиБ. Границы включительно допустимы. После исправления причины обычный ручной или автоматический
повтор снова соберёт архив.

Импорт принимает только ZIP с известным размером не больше 20 МиБ и восстанавливает белый список:

- `subscribers.json`;
- `blocked_users.json`;
- `known_users.json`;
- `user_alerts.json`;
- `stats_current.json`;
- `event_journal.json`;
- `notification_progress.json`;
- `update_state.json`;
- `facts.json`;
- `quarters/*.json`.

До чтения содержимого архив отклоняется, если в нём больше 256 записей, отдельный восстанавливаемый
JSON больше 8 МиБ или суммарный размер восстанавливаемых данных больше 32 МиБ. Границы включительно
допустимы. Пути с абсолютными именами, обратными слешами и сегментами `..` не восстанавливаются.

Повреждённый `event_journal.json`, `notification_progress.json`, `facts.json`, `known_users.json`, `user_alerts.json` или актуальное служебное состояние
автоматических бэкапов или идентичности подписок внутри `subscribers.json` — строгая ошибка всего кандидата: импорт отменяется
до публикации и не заменяет ни этот файл, ни остальные файлы из архива. Это отличается от обычного
неподдерживаемого или повреждённого файла, который можно безопасно пропустить.

Архив с журналом должен содержать соответствующий `stats_current.json`: бот проверяет их общую
привязку и ход обработки. Неполный или несогласованный набор отклоняется целиком. Архивы
с разделённым журналом должны также содержать соответствующий `notification_progress.json`;
файл прогресса без своего журнала не восстанавливается. Прежний цельный журнал остаётся совместимым.
При его восстановлении старый локальный файл отдельного прогресса удаляется с тем же откатом при ошибке.
Старые архивы
без журнала по-прежнему подходят: они сохраняют локальный журнал, не повторяют уже завершённую
историю и оставляют незавершённые события для последующей обработки по исходному кварталу.
Новая копия сохраняет очередь, состав получателей, попытки и итоги доставки, идентичность подписок,
нераспределённые даты, исходные кварталы и подтверждённые ревизии
корректировок. Их связь с журналом и замороженным отчётом проверяется до восстановления.

Любое успешное восстановление останавливает старые попытки обработки, даже если данные совпадают
с текущими или восстанавливается другой файл. Новая попытка читает восстановленное состояние.
Восстановление старого полного набора может повторить уже отправленные после его создания сообщения.
Архив с прежним журналом мигрирует тихо по своей отметке обработки. Старый квартальный архив
без журнала сохраняет локальную очередь. Если архив заменяет только подписчиков без их новой
идентичности, такие подписки считаются новыми и не получают прежнюю очередь.
Все подходящие JSON сначала проверяются как единый кандидат и подготавливаются, затем публикуются под
общей блокировкой. Подписчики сверяются с текущим или восстановленным списком блокировок:
заблокированные пользователи удаляются, а снятие блокировки никогда не возвращает подписку.
Исправный архив может заменить повреждённые текущие файлы, включая файлы с неверной кодировкой.
Если публикация одного файла завершается ошибкой, процесс пытается вернуть точные исходные байты
уже заменённых файлов и удалить файлы, созданные этой попыткой.
Это транзакция ошибок внутри работающего процесса, а не гарантия атомарности при внезапном
отключении питания.

Автоматические бэкапы:

- после накопленных подписок и отписок, но не чаще одного успешного раза за 24 часа;
- при смене квартала;
- раз в семь дней как fallback после последнего успешного автоматического бэкапа;
- при штатном завершении Python/Docker, если недавний бэкап не был только что доставлен.

Доставка квартального отчёта и связанного с ним бэкапа отмечается независимо: сбой одного этапа не
должен скрыть необходимость повторить другой. Квартальный бэкап обновляет общий автоматический
таймер, но не удаляет накопленные изменения подписок. Ручной и shutdown-бэкапы этот таймер и
накопленное состояние не меняют.

Portable-версия для Windows не отправляет финальный бэкап при остановке. Событийные, квартальные,
еженедельные и ручные копии во всех режимах продолжают работать. Доставка всегда идёт напрямую по
`OWNER_ID`, поэтому владелец должен предварительно начать диалог с ботом.

Shutdown-backup страхует только штатное завершение. `SIGKILL`, нехватка памяти, потеря питания или
слишком короткий grace period могут завершить процесс раньше доставки архива.
Восьмисекундный timeout — срок завершения всей попытки, а не обещание мгновенно оборвать уже
начатую операцию с файлом: после истечения срока бот выполняет только короткое кооперативное
завершение текущего ограниченного шага. Сжатие, повторы и отправка не продолжаются в фоне после
возврата shutdown-хука.

### Проверка обновлений и Windows-релизы

`project_meta.PROJECT_VERSION` описывает текущую версию исходников и может быть новее последнего
опубликованного portable-релиза. Режим запуска из исходников показывает эту версию напрямую.
Локальная сборка Windows EXE без релизного тега получает суффикс `-dev`.

Команды `/info` и `/version` разделяют три разных значения:

- **Версия этого бота** — версия, на которой сейчас работает этот экземпляр;
- **Актуальная версия проекта** — последняя известная версия ShikiUpdatesBot;
- **Последняя версия для Windows** — последняя известная portable-сборка.

Там же показаны uptime, последняя успешная полная синхронизация, последний автоматический backup и
активность notification polling. Если какие-то сведения ещё не получены, они отображаются как
неизвестные.

При запуске из исходников, Docker и официальной portable-версии бот обновляет эти сведения раз в
сутки, а владелец может сделать это вручную командой `/version`. Для промежуточной dev-сборки
проверка релиза недоступна. Учитываются только SemVer-релизы с Windows x64 ZIP. Уведомление о
доступном обновлении относится только к Windows-сборке. Ошибка GitHub не останавливает бота, а
уведомление о новой версии повторится только после неудачной доставки или появления ещё более новой
версии.

### Healthcheck и ответственность за перезапуск

Python и Docker запускают HTTP-сервер на `0.0.0.0:$PORT`; portable-версия для Windows его не
запускает.

| Endpoint | Ответ |
|---|---|
| `GET /` | `200` — HTTP-сервер принимает запросы |
| `GET /health` | `200`, пока фоновая проверка считается живой; `503` при её остановке, зависшем старте или устаревшем heartbeat |

Пока бот ждёт доступности владельца перед запуском фоновой проверки, `/health` возвращает `200`;
владелец может запустить её командой `/start`. После запуска задача получает три `CHECK_INTERVAL`
до первого heartbeat: при стандартных настройках это 45 минут. Завершение задачи сразу даёт `503`.
После первого heartbeat тот же порог ограничивает время с последней успешной проверки.
Повторный запуск завершённой задачи получает новый срок ожидания первого heartbeat.
`PORT` должен быть целым числом от `1` до `65535`; некорректное значение заменяется на `8080`.
Ошибка запуска HTTP-сервера пишется в лог, но не останавливает Telegram-бота.

> [!IMPORTANT]
> Healthcheck обнаруживает сбой фоновой проверки, но сам никого не перезапускает. Хостинг,
> оркестратор или внешний монитор должны регулярно вызывать `/health` и иметь собственные правила
> перезапуска. Docker `restart: unless-stopped` реагирует на завершение контейнера, а не на HTTP
> `503`.

Рекомендуемые начальные настройки внешней liveness-пробы:

| Параметр | Рекомендация |
|---|---|
| Interval | Около 60 секунд |
| Max failures | 1–2 после получения `503` |
| Timeout | Около 10 секунд |
| Initial delay | Около 15–20 секунд |

Не увеличивайте interval пробы до десятков минут: порог устаревшего heartbeat уже рассчитан внутри
бота. Редкая проба лишь добавит задержку между переходом в `503` и реакцией платформы.

### Ошибки и диагностика

Единичная ошибка Shikimori, сети, парсинга или отправки не должна останавливать фоновую проверку.
Бот пишет traceback в лог, пытается уведомить владельца и ограничивает частоту таких сообщений через
`ERROR_NOTIFY_INTERVAL`. Следующая попытка выполняется после `CHECK_INTERVAL`.

Точный ответ Shikimori о закрытом профиле обрабатывается отдельно: подробная инструкция уходит
только `OWNER_ID` с тем же ограничением частоты, подписчики её не получают, а сохранённые история,
избранное и статистика не заменяются. После открытия списка polling продолжает работу без перезапуска.

Сетевые функции Shikimori различают ошибку и пустой результат. При недоступном экспорте или GraphQL
статистика деградирует без падения и может временно не получить обогащённые метаданные.

Отправка избранного, отчётов и бэкапов ограниченно повторяется при Telegram flood control и временных
сетевых или серверных ошибках: после первой попытки выполняется не больше двух повторов. Постоянные
ошибки не повторяются бесконечно. Если Telegram принял сообщение или архив, но ответ потерялся,
повтор может создать дубль. Поздний отказ не доказывает, что первая отправка не состоялась.
Отчёты и автоматические бэкапы отмечаются доставленными только после подтверждённого успеха;
до него сохраняются исходный отчёт и необходимость повторной отправки. После неоднозначной
Rich-отправки бот сохраняет её формат даже через перезапуск: другой формат мог бы повторить уже
полученный фрагмент. При неоднозначном исходе интерактивный отчёт сообщает, что сообщения могли
прийти и повтор может создать дубли. Уведомления о событиях истории используют сохранённую
очередь и отдельные ограничения, описанные выше; гарантии exactly-once нет.

Portable-версия для Windows пишет в консоль и `logs/bot.log`: один файл ограничен 2 МиБ,
сохраняются три резервные ротации. Python/Docker пишет в стандартный вывод, который нужно собирать
средствами терминала, Docker или хостинг-платформы.

При исчерпании inline-лимита журнал записывает актуальные Telegram ID, имя и username последнего
потребителя и первого отклонённого пользователя, а также расход по всем участникам текущего окна.
Текст поискового запроса не логируется. Portable-логи остаются в локальной папке `logs/` рядом с exe и не
входят в `/backup`.

Если процесс полностью завершился, Telegram недоступен или сеть блокирует соединение, бот не сможет
сам отправить аварийное сообщение. Нужны внешние логи, мониторинг и корректная restart policy.

### Разработка и тестирование

Проект использует Python 3.12, [aiogram 3.31+](https://docs.aiogram.dev/) для Telegram,
[aiohttp](https://docs.aiohttp.org/) для HTTP, [Docker](https://www.docker.com/) для контейнерного
развёртывания и публичные REST/GraphQL endpoints [Shikimori API](https://shikimori.io/api/doc).

Внутреннее устройство и стабильные контракты описаны в
[ARCHITECTURE.md](ARCHITECTURE.md). Процесс работы с репозиторием находится в
[AGENTS.md](AGENTS.md).

Модули приложения находятся в `src/` и используют плоские имена импортов.
Основная точка входа `main.py` и публичный файл метаданных `project_meta.py`
расположены в корне репозитория. Для запуска из исходников и на хостинге
используется команда `python main.py`. `pytest.ini` подключает `src/` и корень
для тестов; monkeypatch-цели используют плоские имена, например
`handlers.fetch_favourites`.

Установка runtime и test dependencies:

```bash
pip install -r requirements.txt
pip install -r requirements-dev.txt
```

Основные проверки:

```bash
pytest tests/
ruff check .
git diff --check
```

Дополнительные варианты запуска pytest:

```bash
pytest tests/test_handlers_notify.py -v
pytest tests/ -v --cov
```

`tests/conftest.py` автоматически задаёт тестовые `BOT_TOKEN`, `OWNER_ID`, `SHIKI_USER` и отдельный
`DATA_DIR`; использовать реальные секреты для тестов не нужно.

Workflow сборки Windows-релиза принимает строгий тег, совпадающий с `PROJECT_VERSION`, собирает EXE,
создаёт `ShikiUpdatesBot-windows-x64.zip` и отдельный `.sha256`. Проверка VirusTotal запускается
только для сборки по тегу и носит информационный характер. Отсутствующий secret, rate limit, timeout
или обнаружение не блокируют создание черновика Release; публикация остаётся ручным решением
владельца.
